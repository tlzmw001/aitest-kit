# 后端实施规格 · 数据库、持续采集与清理

交付对象是独立日志平台。S1 建立可运行的配置、迁移和容量原型，S2 接入真实消费循环，S3 实现后台清理与容量保护。API 和 worker 使用独立进程、连接池及启动入口。开发和测试以[配置契约](../log_capture_platform_configuration.md)为准，查询返回及 HTTP 错误以[接口规格](02_http.md)为准。

## S1　配置、数据模型和容量原型

**文件归属。** 独立项目使用 `src/log_platform/config.py` 加载并校验配置，`src/log_platform/db/` 放连接池、查询和写入语句，`migrations/` 放版本化 SQL。worker 入口、消费、清理、容量采样放 `src/log_platform/worker/`。测试分 `tests/unit/`、`tests/integration/`、`tests/capacity/`。当前 AITest 仓库是交接文档的存放位置。

**启动。** API 和 worker 读取同一份 `--config` 或 `LOG_PLATFORM_CONFIG`，逐项校验已定义的预算、来源引用、映射和权限。日志只记配置项名与脱敏错误。独立迁移命令创建或升级指定数据库，重复执行已应用版本应安全返回。应用启动核验迁移版本。同一 Linux 实例的 worker 启动时，对配置的数据根目录内的固定锁文件持有排他 flock 至进程退出。重复启动直接报已有实例。这样不会占用给写入和清理预留的数据库连接。API 启动和重启均不启动消费。

| 持久化对象 | 键、写入者及用途 |
| --- | --- |
| 来源、映射与进度 | `source_registry` 以 `source_id` 为主键，绑定真实集群及 topic 身份、group 和启动边界。按 `format_ref` 保留不可覆盖的映射；来源保存解析后的收齐规则及其修订，允许同格式的不同 Topic 使用不同规则。分区格式切点绑定下一起始 offset。`consumer_progress` 主键为 `(source_id, topic, partition)`，保存下一待处理位置、最近成功写入时间和缺口边界。由 worker 更新。 |
| `requests` | 主键 `(source_id, req_id)`。保存首次入库时间、固定桶、冻结的完成规则修订和应收数（如适用）、首次分区、快照版本、有效事件数、已存原文总字节数、end 位置、采集状态、超时原因、expires_at、可用性和防复活期限。同一行串行化消费与删除。精确预删允许建立仅有控制信息的行，此时 first_seen_at、分区、采集状态为空。 |
| `events` | 按请求首次入库时间的 UTC 分钟桶 RANGE 分区。唯一约束含 `(bucket_start, source_id, partition, kafka_offset)`，topic 由 source 唯一绑定。另有定位索引覆盖 `(bucket_start, source_id, req_id, kafka_offset)`。以 bytea 存一份通过校验的 UTF-8 JSON，另存原文字节数、format_ref、接收时间、查询所需标量与 JSONB 维度。稳定事件标识供 HTTP 访问。offset 用 bigint 存储，对外序列化为十进制字符串。 |
| 清理任务与预览 | `cleanup_jobs` 以 job_id 为主键，并对 Token 主体、来源、幂等键的组合设唯一约束，保存操作类型和请求参数摘要。items 按 `(job_id, req_id)` 唯一。预览记录归属、期限和冻结的目标 ID、版本。共用同一 human Token 的用户可查该凭证的任务；Agent 的任务按其独立 Token 归属。API 受理，worker 写执行回执。 |
| 下载票据 | `export_links` 以随机票据的 SHA-256 摘要为主键，记录签发凭证的稳定身份、source_id、精确有序 reqIds、各请求版本、issued_at 与 expires_at；按 expires_at 建索引。仅存键、范围与期限等控制元数据，原始票据、API Token、下载 URL、日志正文、压缩文件均不入表。 |

PostgreSQL 分区表的唯一约束须包含分区键。跨分钟桶重放由每分区事务锁定进度、检查 next_offset 后再路由解决。重启碰到旧 offset，即使原事件所在桶已回收，也不能重新建桶插入。过滤使用参数化 SQL，只接受来源声明的字段。请求列表的多个维度条件在同一事件上匹配。首版索引优先覆盖请求定位、到期扫描及分区内事件读取；对已声明维度使用查询计划与实测决定索引，避免全原文索引。[PostgreSQL 分区限制](https://www.postgresql.org/docs/18/ddl-partitioning.html#DDL-PARTITIONING-DECLARATIVE-LIMITATIONS)

**S1 容量原型。** 通过同一批量写入与分区策略持续写入实测大小的 JSON，使用独立测试库，记录输入大小分布、可压缩性、写入速率、索引/WAL/临时文件和整桶回收耗时。使用脱敏实样或与实样大小及可压缩性相符的载荷。每秒 30 个请求、每个 100 条，平均 10,000 B 时原始输入 30 MB/s，300 秒约 9 GB；全为 50,000 B 时约 45 GB。这两个数只描述原始载荷。先验证平均场景是否有周转余量，再投入完整页面与接入开发。S3 通过后用正式 worker 重跑同一组场景。

**S1 验收。** 在干净 PG 18 实例执行迁移、重跑迁移并启动两个进程。配置引用错误时启动失败并指明字段，同一 worker 的第二个实例不能接管。插入两个来源的同名请求，按请求和来源能只读到各自的事件。提供数据卷占用曲线、写入和回收记录，说明 20 GB 额度覆盖范围与未测项。

## S2　持续消费和请求完成

**来源生命周期。** 每个启用来源有独立 Consumer 与执行线程，消费端主动连接 broker。绑定 cluster、topic 和 group 后订阅该 topic。首次分配持久化 earliest/latest 选定的启动边界并设置读取位置。已有进度从数据库恢复，检查 broker 的低/高水位和 topic 身份。进度越界或身份失配时保留旧值、报告缺口并停止该来源继续推进。首次 latest 接入须等分区就绪后再发需要完整判断的新请求。停用来源可继续查询已有数据。变更 topic 或重建 topic 启用新的 source_id。

**消费循环。**

1. 仅消费线程调用 poll、处理分配/撤销和提交 Kafka 进度。固定关闭 `enable.auto.commit` 和 `enable.auto.offset.store`，`auto.offset.reset=error`。poll 单次等待至多 100 ms，并服从未刷新批次的剩余时间。空闲后继续轮询。[Consumer API](https://docs.confluent.io/platform/current/clients/confluent-kafka-python/html/index.html#confluent_kafka.Consumer.poll)
2. 各来源轮流向有界写入调度器提交分区内有序的批次。达到 500 条、4 MB、最老消息等待 100 ms 中任一条件即调度；单分区仅一个写事务在途，全局最多两个。应用队列与在途载荷总计 64 MB，客户端预取另按来源分摊 64 MB 目标。队列满时暂停相关分区，继续 poll 和回调。按来源记录停顿原因。
3. 事务内锁定分区进度，按实际投递顺序处理记录。跳过 offset 小于已持久化 next_offset 的重放。每个可归属请求通过相同唯一键 upsert 再锁行，包括尚无请求行的首次写入与预删竞争。一批涉及多行时各路径统一排序锁定，重试死锁或短暂故障要重跑整个事务。已知缺口、删除或到期标记的处理与进度同事务持久化。
4. 写入事件、请求汇总、可用性/采集状态，将 next_offset 更新为本批实际处理的最后一个 offset 加 1，然后提交。消费线程收到已提交回执后提交 Kafka 的下一读取位置。同批后到的 end 可在一次数据库提交中与前置事件一起可见。数据库失败时回滚整批。Kafka 提交失败依赖数据库进度重试和恢复。不能仅因两个可见 offset 之间有数值间隔就推断漏发，缺口须来自水位越界、损坏记录等实证。
5. 撤销/丢失分区时停止旧分配派发，收敛或回滚在途事务。使用分配代次隔离回执，旧代次不能提交新代次的 Kafka offset。重新分配后按数据库进度启动。日志停写、数据库背压和短时断网期间继续服务 poll；停进程时有界收敛，只提交已持久化位置。

**报文读取。** 先核对完整 UTF-8 字节数，按配置的显式 JSON Pointer 读取一条 JSON 对象。请求 ID 必须是非空字符串，保留大小写及前导零。普通业务新增字段保留在完整报文中。正文可为完整对象、数组、字符串或 null。配置了正文路径但实际缺失时省略 `data`，显式 null 则返回 `data: null`。结束匹配要求 JSON 类型和值都相符，布尔 true 与整数 1 不相等。切换映射版本需先排空旧流的在途请求及积压并记录每分区切点。详情和导出依事件保存的 format_ref 解释原报文。

原文视图直接返回已校验 JSON，规范化正文与导出用无损数字解析和编码。测试包含大整数 `9007199254740993` 和高精度小数，分别与原报文对读，使 Python、PostgreSQL 与浏览器间往返的精度损失可被发现。

| 输入或条件 | 在同一持久化边界内产生的结果 |
| --- | --- |
| 首次看到请求、配置 END | 固定首次分区、桶、first_seen_at、expires_at 和等待截止时间，状态为 COLLECTING，之后普通事件只增加数量、字节数和版本。 |
| 计数来源收到有效事件 | 在 (source_id, reqId) 的事务锁内按冻结规则去重、写事件并累计，不要求同分区。少于 N 为 COLLECTING，恰为 N 且无缺口为 COMPLETE，超过 N 为 INCOMPLETE。N=1 时首条即可完成，计数来源没有 end_offset。见[来源级计数与并发规则](07_observed_topic_handoff.md)。 |
| 首次看到请求、completion 为 none | OBSERVED，completion_basis=none。支持查询、清理、导出，完整性未知，无等待 end 的超时任务。 |
| 正常 end | 校验同分区、生产端成功收口契约及已知缺口。此前日志和本条已持久化后转 COMPLETE，记录 end_offset、completion_basis=producer_end、新版本。事件数包含已存结束事件。 |
| 可归属的坏记录、超过 50,000 B 或 100 条、END 来源跨分区发送 | 可归属的请求标 INCOMPLETE，记录原因及 Kafka 位置。超限部分不继续写大载荷。已有有效原文可查；INCOMPLETE 不因后续 end 恢复 COMPLETE。 |
| 已 COMPLETE 后重放或额外到达 | 同分区同 offset 重放及已确认的业务重投按来源策略去重。新增有效事件或另一个有效 end 属于生产协议异常，记录诊断，转 INCOMPLETE 并递增快照版本。 |
| COLLECTING 达到截止时间 | 转 TIMED_OUT。超时扫描与接收 END 或计数事件的事务锁同一请求行，并核对数据库当前时间与截止时间，使结论与扫描调度顺序无关。超时后的收口事件或计数事件保留迟到诊断及可用证据，不翻转为 COMPLETE。 |

**无法归属的坏消息。** 按来源、分区、offset 记录有界错误代码和大小，保留分区缺口事实，再推进该条消息的进度。错误记录不含完整载荷。对可能受影响的在途请求及无法排除丢了首条事件的请求禁止发布 COMPLETE。保守实现可设分区完整性标记并累计计数，见到正常 end 仍继续提供查询。只有能圈定缺口影响范围时才恢复正常完成判断，例如业务受控停发、排空旧请求后记录的新分区读取边界。错误样本轮转不能擦除缺口事实。超大报文无法在原始字节上限内安全提取 ID 时走此路径。

**S2 验收。** 在测试 Kafka 的两个来源分别发平铺广告协议、嵌套订单协议，各使用同一 reqId。worker 空闲后也能接收，同分区按 offset 展示，正常 end 之前全部数据可查，来源间结果隔离。测试中注入“DB 提交前退出”“DB 提交后 Kafka commit 前退出”“失去分区后收到旧批次回执”，分别核对 DB 位置、Kafka 恢复位置、事件数与快照版本。再覆盖未收到 end、无 end 契约、未知 reqId、毒消息、超限及 end 后异常，结果与上表一致。有界等待使用事件、数据库可查询条件或可控时钟。

## S3　清理、过期和 20 GB 容量保护

**受理与防复活。** 精确清理按授权的 source 和 reqIds 校验，事务内写任务、精确目标及请求删除标记。首次受理时即使日志未到也占住相同请求键。数据库提交后 API 返回 202，查询从此隐藏相应载荷。多次提交同一幂等键和等价请求返回原任务，不同内容报冲突。已有请求需区分相同授权前缀下的多个调用方。清理期间消费端仍检查并锁定控制行，有效标记下只更新诊断和进度。首次入库起算的 300 秒 TTL 对所有来源生效，查询和消费按同一绝对 expires_at 判断，定时扫描的延迟不能延长可见性。

**前缀清理。** 对单来源执行字面 startswith。预览冻结具体 ID、快照版本与范围，忽略等待 end 的 COLLECTING，标出 OBSERVED 的完整性未知。匹配数超预览上限时返回缩小范围的错误。提交时重新鉴权，按冻结集合逐项锁定；版本变化或已经不可用返回相应逐项目结果。预览过期后不能首次提交，已受理任务仍可按幂等键找回。具体结果枚举和 HTTP 优先级见接口规格。

**后台回收。** 每秒扫描一次，到达 100 个待处理请求或最老等待达到 5 秒即执行。单事务最多 100 个请求、1000 事件、10 MB 载荷，按先达到的限制分批。目标状态、成功删除的事件和任务进度在同事务中提交。任务按 ACCEPTED → RUNNING → DONE / PARTIAL_FAILED / FAILED 演进。进程退出后继续未完成的目标，已执行项可幂等重试。DONE 表示对应载荷已清理。保留删除/过期控制信息与终态任务 1 小时，期限从丧失可见性或任务终止算起。活跃任务不可因元数据 TTL 消失。

**分钟桶。** 预建当前与下一桶。首次写入在事务内确定固定桶，后续事件沿用。只有桶内所有请求均超过各自 expires_at 或已被释放、在途写事务已收敛时才能回收该桶。清理与写入协同锁定桶或通过分区 DDL 锁进行二次校验，避免事务在已回收桶补写。整桶回收保留请求元数据、幂等记录和分区位置。普通 DELETE 及 VACUUM 的页复用情况与卷实际可用字节分别记录。[PostgreSQL 空间回收](https://www.postgresql.org/docs/18/routine-vacuuming.html)

**票据签发、兑换与回收。** API 验证 Bearer 的逐项 export 权限，在一个数据库快照中确认来源、原始目标和版本，生成至少 256 位密码学安全随机票据。有效期取配置时长（默认 60 秒）与所有目标剩余 TTL 的最小值。在受控事务内串行检查活跃数及控制元数据预算并登记摘要，提交后将票据仅通过签发响应交给客户端。全局活跃数上限默认 100，同身份和精确目标集合的并发重复签发限流。GET 处理用摘要定位票据，复核原调用方的当前授权，在同一有界导出快照内判断可用性与版本；共用即时导出的并发、内存及发送策略。失败结果见[HTTP 票据语义](02_http.md#41-给远程-agent-和普通-fetch-的下载链接)。GET 重试不续期。worker 随控制元数据清理循环按期限索引小批回收过期票据；签发、下载和回收均不延长数据 TTL。访问日志在写入前对下载 path 使用路由模板，错误及监控同样屏蔽票据原文。

**远程下载入口。** 所有普通 REST 与 MCP 使用 Bearer 校验身份及 grant。人类 Token 与 Agent Token 独立配置。远程 Agent 优先用 httpx 经隧道直接 POST 即时导出，流式保存文件；只支持普通 GET 的工具用短票。download_url 从 `server.download_url_env` 指定的可信隧道 origin 生成，未配置则回退公开地址。web_url 始终使用 `server.public_url_env`。配置的两项入口用于 Host/Origin 校验，多用户桥接入口按 server.additional_host_envs 精确扩展 Host 校验，服务端不依赖传入的 Host 或转发头生成外部地址。

**容量控制。**

- 按实际配额使用量、文件系统可用空间、WAL/临时文件及在途批次核算可写余量。专用卷或硬配额覆盖 PG 数据、索引、WAL、临时文件、平台运行日志。容量采样失效应暂停增加载荷并显示原因。清理与状态写入预留可用空间、连接和执行名额。
- 预计下一批可能触及暂停水位（默认 16 GB）时，优先回收已提交清理及到期数据。仍不足则暂停所有来源的拉取/载荷写入、保留未提交进度。继续 poll、清理、查询和健康汇报。磁盘压力本身不触发清除用户仍可读的未到期日志。当实际剩余额度和文件系统余量均至少 5 GB 且 WAL 允许时再逐批恢复。
- 错误摘要、冻结集合、待清理目标、任务元数据及运行日志执行配置中的全局上限。受保护的元数据预算不足时显式拒绝新工作，继续收敛已受理任务。诊断、导出缓存和重试均不能形成未计入额度的第二份长期日志。
- API 需能读取 worker 的持久状态或心跳，呈现来源连接/暂停状态、lag、最近入库时间、已知缺口、全局容量及暂停原因。worker 停止或长期无心跳应能被区分于“消费者在线且当前无消息”。无有效观测的指标返回空值。

| 成功用例逐请求清理、重复提交、先删后到、TTL 与写入竞争 | 每个受理任务可找回，回执与实际载荷一致，迟到数据在标记有效期内不会复活，同名其他来源仍可读。覆盖 worker 在批次提交前后的退出与恢复。 |
| 多轮周转 | 所有来源合计 30 请求/s × 100 事件，平均 10 KB，至少连续 30 分钟。报告是否模拟成功即清理、相应比例与延时，另给仅 TTL 基线。记录实际输入/入库数、lag、延迟分布、卷峰值、WAL、分区回收耗时及有无暂停。稳态 lag 不能持续增长，回收后有可观测可用空间。 |
| 持续极限输入 / 配额不足 | 在隔离额度内用 50 KB 流量且不提前删除，观察全局暂停、清理可用、消费位置不越过未写记录、实际用量不超过 20 GB。容量恢复后重放追平；若 Kafka 保留边界已越过则显示缺口。记录采样间隔和实测峰值。 |
| 并发下载、清理、来源故障 | 慢下载释放 DB 读事务后发送，不能阻止整桶回收。一个来源断联不阻塞另一来源。全部来源共享连接、写批次、配额和导出预算。恢复后核对请求/事件数量及各状态。 |
| 短时直链与重启 | 签发后重启 API，仍能在有效期用普通 GET 下载同一冻结版本；并发兑换遵守共享上限，撤权、删除及版本变更均阻止下载。并发签发和元数据空间不足时不超活跃票据上限，过期项可批量回收，数据库只保留摘要和控制元数据。 |
| 隧道即时导出与 Bearer | 使用 Agent 的真实隧道入口及 agent Token 直接 POST 正常返回压缩附件；未带或失效凭证为 401，越权动作 403。验证 human 与 agent 的任务归属、两种外部 URL 的可信 origin 及单地址回退。 |
