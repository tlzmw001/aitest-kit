# AITest Kit 多 Topic 日志断言 · 实施入口

**评审目标**　在一次业务调用后，允许用例分别验证主链路、性能、入湖等来源。日志平台负责判断各来源是否收齐。Kit 负责在用例截止时间内取证、执行内容断言、汇总报告和提交成功清理。本文档组是基于 v0.7.0 的增量设计，四个分片均待实现。

相关文档：[Kit 总体评审稿](../multi_topic_review.md) · [日志平台 v1 升级契约](../../log_capture_platform_delivery/07_observed_topic_handoff.md) · [平台联调数据](../../log_capture_platform_delivery/05_acceptance_vectors.json)。

## 一条用例如何运行

假设用例只验证主链路和性能日志。入湖也是一个已配置的来源，但这条用例没有对应断言。

| 时机 | 平台和 Kit 的行为 |
| --- | --- |
| 发出业务请求 | Harness 按该服务约定启用采集，一次绑定本次调用的关联 ID。Kit 为两个所需来源登记同一步骤的截止时间。pytest 执行即时断言，并按配置的用例并发数继续调度。 |
| 第一轮状态查询 | 后台用一次批查发送主链路和性能两对 `(source_id, reqId)`。主链路若已 `COMPLETE + AVAILABLE` 就进入取证队列。性能若仍在收集则留到下一轮。 |
| 主链路取证 | 按来源、ID 和刚取得的版本读取所有事件页，本地执行该来源的各组字符串断言。已完成的来源退出轮询。 |
| 性能日志到齐 | 以相同方式读取平台确认的快照。整例通过后，只对显式声明 `on_success` 的来源提交精确清理。整例在报告中计一次。 |
| 性能一直未齐 | 新多来源步骤在健康轮询下到期，记为 `FAILED / LOG_READINESS_TIMEOUT`。保留主链路已得结果和性能最后一次观测，两个来源都不提交清理。 |

并发有两个旋钮。`case_concurrency` 限制同时执行的用例，设为 1 时用例串行。`log_concurrency` 限制后台同时取证和检查的任务，设为 1 时依次处理已就绪的来源。尚待收齐的请求都可以留在轮询队列。步骤登记时确定等待期限，重试、翻页及恢复沿用原截止时间。

## 配置由谁维护

| 位置 | 维护内容 |
| --- | --- |
| 日志平台的 `log-platform.yaml` | 每个来源的集群、topic、业务字段映射、END 或去重后的应收条数、权限、TTL 和容量。 |
| Kit 工作区的 `aitest_config/log_assertions.yaml` | 自动加载；声明平台入口、凭证变量名、并发与超时。升级后优先用 `platform.base_url`，省略时沿用 `base_url_env`。云端新任务可把自己可达的隧道 HTTP 入口写在这里。 |
| 模块的 `module.yaml` 与 Harness | 模块把来源别名映射到平台的 `source_id`。Harness 决定怎样生成或取得关联 ID，以及如何向业务请求传入采集参数。 |
| Suite profile 的 `log_assertions` | 每个断言组选择步骤和来源，写 `select`、字符串 `checks` 及可选清理策略。多个组可共享一个来源快照。 |

**新旧边界**　以请求步骤为单位。步骤内只要有一组显式选了 `source`，该步骤全部组使用可追溯到实际来源的新语义；未指定来源的组继续取模块默认来源。整个步骤都沿用旧写法时，保留旧生成结果和结算分类。已开始的 run 保持原连接绑定、断言输入和期限，恢复继续消费既有证据。

**开发验收入口**　先在仓库根目录运行下面的旧行为回归。各片文档给出新增的失败场景、入口和验收断言。完成第四片后再跑完整测试、构建安装包并从安装后的 CLI 验收。

```bash
python3 -m pytest -q tests/test_log_platform_client.py tests/test_log_assertion_profile.py tests/test_log_assertion_binding.py tests/log_assertions
```
